Project 15: SPC Control Chart & Capability Dashboard with Automated Alerts

Tujuan project: membangun dashboard SPC yang memantau kekuatan ikatan glue pada proses perekatan lensa lampu depan sepeda motor dari hasil force push test, untuk mendeteksi proses yang mulai keluar kendali atau Cpk yang turun di bawah 1,33 sebelum banyak produk NG terbentuk, sehingga tindakan perbaikan bisa diambil lebih awal.

Kategori:Rancangan projectManufaktur sepeda motorData simulasi tiru data kerjaSPC + dashboard + alert

Project Introduction

Bayangkan warung bakso yang menjual ratusan bakso setiap hari. Pelanggan meminta berat bakso antara 15 dan 40 gram. Setiap jam, pemilik warung menimbang 5 bakso. Selama ini ia hanya bertindak jika ada bakso di bawah 15 gram, padahal saat itu sudah banyak bakso kecil yang terjual.

Pemilik yang lebih jeli mencatat berat rata-rata 5 bakso itu di sebuah grafik. Jika rata-rata mulai turun pelan-pelan beberapa jam berturut-turut, ia langsung memeriksa adonan, meski belum ada bakso yang ditolak. Grafik seperti itu disebut control chart.

Project ini membangun dashboard SPC dengan alert otomatis: hasil push test dari file CSV mesin dikumpulkan dalam satu database, lalu dihitung menjadi control chart dan Cpk. Sistem memberi peringatan saat ada pola yang tidak wajar. Datanya adalah data simulasi yang meniru struktur file mesin karena data pabrik bersifat rahasia. Kata bergaris bawah putus-putus kuning bisa diklik untuk melihat artinya.

Gambaran alur kerja di perekatan lensa lampu sepeda motor

Proses ini bisa dibayangkan sebagai tiga jalur. Dua jalur pertama sudah berjalan di pabrik. Jalur ketiga adalah yang dibangun di project ini.

  1. Jalur produksi. Lensa lampu dipasang ke rumah lampu, glue diberikan, lalu glue dikeraskan dengan sinar UV dan oven. Kekuatan ikatan glue menentukan apakah lensa tetap di tempatnya selama produk dipakai.
  2. Jalur pengujian. Beberapa sampel diambil sebelum dan sesudah oven, lalu didorong mesin push test sampai lepas. Gaya saat lensa lepas (gram) dicatat ke file CSV.
  3. Rekap manual saat ini. Setiap file direkap dengan macro VBA dan Excel menjadi Max, Min, Avg, dan CPK per file. Angka tidak dilihat sebagai tren, sehingga tindakan baru diambil setelah ada NG.
  4. Jalur data baru. File CSV dibaca otomatis ke database, dihitung menjadi control chart dan Cpk, lalu ditampilkan di dashboard. Alert muncul saat pola tidak wajar terdeteksi, sebelum NG menumpuk.

1. BackgroundKenapa tema ini dipilih

Latar belakang masalah

Hasil force push test perekatan lensa lampu disimpan sebagai satu file CSV per run. File direkap dengan macro VBA dan Excel menjadi Max, Min, Avg, dan CPK per file. Cara ini membuat beberapa masalah:

  • Angka dilihat per file, bukan sebagai tren. Penurunan kekuatan glue yang pelan selama beberapa hari tidak terlihat.
  • Tindakan baru diambil setelah ada hasil di bawah 1500 g. Saat itu, produk dari run sebelumnya mungkin sudah terdampak.
  • CPK dihitung dari sedikit sampel per file, sehingga angkanya naik-turun dan sulit dipercaya.
  • Belum ada aturan tertulis kapan suatu hasil dianggap tidak wajar, sehingga keputusan bergantung pada pengalaman orang yang membaca.

Alasan memilih tema ini sebagai portofolio

  • Dekat dengan pekerjaan sehari-hari. Struktur file mesin push test dan spec 1500–19000 g sudah dikenal, sehingga konteks bisnisnya bisa dijelaskan dengan meyakinkan saat wawancara.
  • Menunjukkan skill Data Analyst yang jarang dimiliki. Statistical process control, analisis capability, SQL, dashboard, dan aturan alert yang otomatis.
  • Tingkat kesulitan sedang. Rumus SPC baku, tetapi perlu ketelitian dalam memilih baseline, memeriksa distribusi data, dan menekan false alarm.
  • Terhubung dengan project lain. Memakai jenis data yang sama dengan Project 12 (Process Comparison Analysis) dan Project 20 (Push Test Data Pipeline + Dashboard). Pipeline di Project 20 bisa menjadi sumber data otomatis untuk dashboard ini.

4. DatasetData simulasi yang meniru struktur file CSV mesin push test

Kenapa data simulasi? Data pabrik bersifat rahasia. Program Python membuat file CSV dengan struktur yang sama seperti file mesin push test: satu file per run, berisi beberapa sampel dan nilai gaya dalam gram. Pola nyata ditiru: hasil sesudah oven lebih kuat, ada sedikit perbedaan antar model, dan ada kejadian khusus yang sengaja ditanam. Karena kejadian itu diketahui, kita bisa memeriksa apakah control chart dan alert berhasil menemukannya.

Ukuran: 2 model, 2 kondisi (sebelum dan sesudah oven), 2 shift, 2 mesin uji, sekitar 75 hari kerja. Usulan awal 5 sampel per run. Perkiraan: ±600 file CSV (run) dan ±3.000 baris hasil ukur. Jumlah pastinya baru diketahui setelah data dibuat.

Fakta yang sengaja ditanam (ground truth)

1. Model B sesudah oven mengalami penurunan kekuatan bertahap selama ±1 minggu (usulan: glue lot baru), sampai Cpk di bawah 1,33 dan muncul beberapa NG.

2. Model A sebelum oven mengalami penurunan mendadak selama 3 hari di satu shift (usulan: nozzle glue tersumbat sebagian).

3. Satu mesin uji menunjukkan sebaran yang membesar selama ±2 minggu (terlihat di R chart, rata-rata tetap).

4. Hasil sesudah oven secara sistematis lebih tinggi daripada sebelum oven, sehingga kedua kondisi perlu chart terpisah.

5. Sekitar 2–3% data kotor disisipkan: angka berformat koma desimal dan titik ribuan, nilai kosong, nilai 0 (sampel tidak teruji), file ganda, dan nama model salah ketik (misalnya "Model-A").

Empat tabel yang akan dibuat

Data disimpan dalam beberapa tabel yang saling terhubung lewat kolom yang sama (misalnya run_id dan model). Satu file CSV menjadi satu baris di tabel test_run dan beberapa baris di tabel measurement.

5. ToolsAlat yang dipakai dan alasannya

Python (pandas, NumPy, SciPy)

Membuat file CSV simulasi, membaca dan membersihkan file mesin (termasuk angka koma desimal), serta menghitung uji normalitas dan Cpk. Pengacakan dikunci dengan seed agar data bisa dibuat ulang.

Bahasa paling umum di lowongan Data Analyst. SciPy menyediakan uji statistik siap pakai.

DuckDB + SQL

Database tempat semua tabel disimpan. SQL dipakai untuk menghitung rata-rata dan rentang per subgroup, control limit, dan aturan alert dengan window function. Disimpan sebagai view agar dashboard memakai rumus yang sama.

Gratis, tanpa server, cukup satu file. Konsisten dengan Project 2 dan Project 3.

Excel

Cek silang: menghitung ulang control limit dan Cpk untuk beberapa kelompok secara manual, lalu dibandingkan dengan hasil SQL (Q14).

Alat yang sudah dipakai di pabrik, sehingga hasil mudah diverifikasi rekan kerja.

Streamlit + Plotly

Dashboard web interaktif: control chart dengan titik alert berwarna, tren Cpk, histogram terhadap spec, dan tabel alert. Dipublikasikan di Streamlit Community Cloud agar bisa dibuka lewat link.

Plotly sesuai kolom Tools di daftar portofolio. Power BI butuh akun work/school untuk publish.

Skrip alert (Python) + GitHub Actions (opsional)

Skrip memeriksa run terbaru terhadap aturan alert dan menulis hasilnya ke alert_log. GitHub Actions dapat menjalankan skrip ini terjadwal dan mengirim notifikasi email atau Telegram.

Aturan ditulis di kode, bukan di kepala orang, sehingga keputusan selalu sama.

GitHub + Markdown

Menyimpan kode, contoh data, dan README berisi masalah, data, analisis, rekomendasi, dampak, dan batasan.

Standar industri untuk portofolio. Recruiter melihat project langsung dari repositori.

Tahap A · Perencanaan

  1. Menyepakati aturan SPC

    Menetapkan ukuran subgroup, jenis chart per kelompok, periode baseline untuk menghitung control limit, aturan alert, dan target Cpk 1,33.

    Hasil: dokumen aturan SPC · Alat: Markdown

  2. Merancang struktur tabel

    Menentukan 4 tabel, kolom, dan kolom penghubung. Mencatat format file CSV mesin yang akan ditiru. Membuat kamus data.

    Hasil: diagram tabel dan kamus data · Alat: Markdown

Tahap B · Menyiapkan data

  1. Membuat file CSV simulasi

    Program Python membuat ±600 file CSV selama 3 bulan dengan format seperti file mesin, termasuk kejadian yang ditanam dan data kotor 2–3%.

    Hasil: folder CSV, skrip generator, catatan ground truth · Alat: Python

  2. Parsing dan membersihkan data

    Membaca semua file, memperbaiki angka berformat koma desimal, menyeragamkan nama model, dan memutuskan baris bermasalah dibuang atau diperbaiki (Q13).

    Hasil: data bersih dan log cleaning · Alat: Python (pandas)

  3. Memasukkan data ke database

    Memuat data bersih ke DuckDB, mengisi tabel spec_limit, dan menambahkan aturan pengecekan agar data yang salah tidak bisa masuk.

    Hasil: file database · Alat: DuckDB

Tahap C · Menghitung dan menganalisis

  1. Menghitung control limit dan Cpk

    Menulis query SQL untuk rata-rata dan rentang per subgroup, control limit dari periode baseline, Cp, Cpk, dan rolling Cpk mingguan. Disimpan sebagai view.

    Hasil: kumpulan view SPC · Alat: SQL

  2. Cek silang dengan Excel

    Menghitung ulang control limit dan Cpk satu kelompok secara manual, lalu memastikan hasilnya sama dengan SQL (Q14).

    Hasil: lembar cek silang · Alat: Excel

  3. Menganalisis stabilitas dan capability

    Menjawab Q1–Q7: kejadian out-of-control, tren Cpk, bentuk distribusi, serta perbedaan antar model dan kondisi.

    Hasil: grafik dan tabel temuan · Alat: SQL, Python (SciPy, Plotly)

  4. Membuat dan menguji aturan alert

    Menerapkan aturan alert pada seluruh data, menghitung jarak alert ke NG pertama, dan jumlah false alarm di periode stabil (Q8–Q10). Aturan disetel jika false alarm terlalu banyak.

    Hasil: skrip alert dan tabel evaluasi · Alat: Python, SQL

  5. Menghitung dampak dan mencocokkan ground truth

    Mengestimasi unit NG yang bisa dicegah per bulan (Q11), melihat pola per mesin, shift, dan lot (Q12), lalu memeriksa apakah kelima kejadian yang ditanam terdeteksi.

    Hasil: tabel skenario dan bagian validasi di README · Alat: Python (pandas)

Tahap D · Menyajikan

  • Kelima kejadian yang ditanam terdeteksi, dan alert muncul sebelum NG pertama pada kejadian penurunan bertahap.
  • Jumlah false alarm pada periode stabil tercatat dan berada di batas yang disepakati (usulan: paling banyak 1 per kelompok per bulan).
  • Orang awam bisa membuka dashboard dan menyebutkan kelompok mana yang sedang bermasalah dalam waktu kurang dari 1 menit.
  • Checklist standar terpenuhi: pertanyaan bisnis, data cleaning, analisis SQL, dashboard ter-deploy, README berisi insight dan rekomendasi.

Ruang lingkup Usulan awal

2 model, 2 kondisi, 2 shift, 2 mesin uji, ±3 bulan. 5 sampel per run sebagai satu subgroup. Control limit dihitung dari 25 subgroup pertama yang stabil (baseline), lalu dikunci. Spec 1500–19000 g dianggap berlaku sama untuk semua model dan kondisi, perlu dikonfirmasi. Dampak dihitung dalam jumlah unit, belum dalam rupiah.

Hal yang perlu diwaspadai Usulan awal

Spec sangat lebar. Rentang 1500–19000 g jauh lebih lebar daripada sebaran data, sehingga Cpk hampir selalu ditentukan sisi bawah. Cpk sisi bawah dilaporkan terpisah agar jelas.

Distribusi belum tentu normal. Kekuatan ikatan sering miring ke satu sisi. Cpk dengan rumus normal bisa menyesatkan, sehingga bentuk distribusi diperiksa dulu (Q5).

Uji destruktif dan sampel kecil. Sampel yang diuji rusak, jadi jumlahnya sedikit. Cpk dari satu run tidak dipakai, hanya dari gabungan beberapa run.

Pola belum tentu penyebab. Alert menunjukkan ada yang berubah, bukan penyebabnya. Penyebab perlu dicek di lapangan. Perbandingan statistik antar kondisi dan model dikerjakan di Project 12.

False alarm. Makin banyak aturan, makin cepat deteksi, tetapi makin sering alarm palsu. Jumlah aturan dipilih dari hasil uji di langkah 9.
